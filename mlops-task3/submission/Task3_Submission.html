6. Data validation and error handling

An order passes three checks before it reaches the model. Every rejection is a clear HTTP 422, and the service keeps running.

LayerRuns onChecks
Pydantic schema (app/schemas.py)every requestRequired fields, types, no NaN or Infinity, batch size ≤ 500
Per-order rules (src/validation.py)every orderDates parseable and promise after purchase; states among the 27 Brazilian states; payment type known; money and weight ≥ 0; counts ≥ 1; coordinates on Earth. None of the 96,470 real orders breaks a rule.
Great Expectations (src/ge_validation.py)every batch70 expectations: column existence (24), numeric ranges (13), coordinates within Brazil's bounding box (4), allowed categories (3), missing-rate limits (22), positive counts (4), no leakage columns (1)

The Great Expectations suite describes a population ("95% of freight values in the usual range", "at most 10% missing coordinates"), so it runs on batches rather than on single orders. One run takes about 0.9 s; one prediction takes about 40 ms.

Policy when validation fails (validation.on_failure):

  • reject (the default): HTTP 422 with the list of problems.
  • flag: the order is scored anyway, and the problems are attached to the response, the log and a Prometheus counter.
  • Problems that make scoring impossible (missing or unreadable dates, non-numbers) always reject, whatever the policy.

7.3 One chain of hashes

At start-up the API looks up olist-late-predictor@production and downloads that version's serving/ files. It checks each file's md5 against the version's tags and against the DVC pointers, and loads the files only if both match. The same md5 therefore appears in four places:

  • the DVC pointer (models/06_model.joblib.dvc)
  • the MLflow version tag (md5_model)
  • GET /model/info → artifacts_md5.model
  • the model_version hash reported in every response

GitHub Actions runs .github/workflows/task3-ci.yml on every push and pull request that touches mlops-task3/. It has three jobs, and each one runs only if the one before it passed:

  1. lint: ruff check . and ruff format --check .
  2. test (needs: lint): pip install -r requirements/dev.txt, then pytest tests/ -v
  3. build (needs: test): builds the image. On main it also pushes ghcr.io/ziadsuleyman/olist-late-predictor:<sha> and :latest, using the workflow's own GITHUB_TOKEN.

So an image is published only after its lint and tests have passed.

A failing test stops the pipeline — the real history

The first CI run of Task 3 failed. On Linux, git had converted the line endings of the JSON artifacts (CRLF → LF), so their md5 no longer matched the DVC pointers, and a test caught it. The build job did not run. The fix was .gitattributes (models/*.json -text), which stores the artifacts byte for byte; the next run was green.

10.3 Prediction distribution and drift

Drift is measured as the PSI of the score distribution against the validation split (warn at ≥ 0.10, alert at ≥ 0.25). The share of orders flagged late cannot show drift, because the alert budget holds it near 5%. The real late rate cannot be the reference either, because it moved from 7.95% to 3.61% between the splits. The score distribution sums up the inputs, so it is what moves.

To show this on the running system, all 18,603 test-split orders were sent to the clean stack's /predict/batch in purchase order, in batches of 500 (36 s in total). /drift was read at the end of each month:

The whole-split figure comes from scripts/analyze_predictions.py --all on the prediction log. The same period is when the delivery promise, the model's most important feature, shrank (median promised days 27 → 19 → 13, June to August) and when ROC-AUC fell from 0.774 (validation) to 0.711 (test).
